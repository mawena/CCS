# Phase 13 (0.11.0) — CCS sur le VPS : plan de construction

> **Pour les agents :** sous-skill requis : superpowers:subagent-driven-development
> (recommandé) ou superpowers:executing-plans, tâche par tâche. Les étapes utilisent des
> cases (`- [ ]`) pour le suivi.

**But :** piloter CCS depuis Internet (version web responsive), depuis un terminal
(`ccs tui`) et depuis le bureau GTK, avec connexion par les comptes Ubuntu et double
authentification obligatoire.

**Architecture :** `ccs-auth` (root, minuscule : PAM, groupe `ccs`, TOTP, sessions,
démarrage des ponts), `ccs-web` (aiohttp, sans droits, `127.0.0.1:8420`), `ccs-bridge`
(un par utilisateur, sous lui : chats, comptes, fichiers, feuille de route, terminaux).
Tous parlent JSON par lignes sur des sockets Unix ; le web, la TUI et le bureau parlent
au pont par la même API.

**Technique :** Python 3.12, asyncio, `python3-aiohttp`, `python3-pyotp`,
`python3-qrcode`, `python3-urwid`, libpam par ctypes, systemd, HTML/CSS/JS sans outil de
construction, xterm.js embarqué, GTK4 / libadwaita pour le bureau.

**Conception :** `docs/superpowers/specs/2026-11-15-phase-13-vps-design.md` (validée le
15/11/2026). La lire avant de commencer.

## Contraintes globales

- Branche `feature/phase13`, partie de `develop` (`git flow feature start phase13`).
- Tout en français (textes, docstrings, commentaires, commits conventionnels), sans
  `Co-Authored-By` ni attribution.
- Tests `unittest` : `tests/test_<module>.py` ; asynchrone par
  `unittest.IsolatedAsyncioTestCase` ; serveur web par `aiohttp.test_utils`
  (`AioHTTPTestCase`, port éphémère) ; graphique sous Xvfb comme en phase 12.
- Aucun test hors de la file Gagarine : `gagarine file "ccs-t-<nom>" 1 1 -- python3 -m
  unittest tests.test_<nom> 2>&1 | tail -5` (graphique : `sh -c 'CCS_GUI_TESTS=1 xvfb-run -a
  …'`). Suite complète une seule fois, par `make deb` (tâche 25).
- Aucun vrai PAM, systemd, nginx, réseau ni `claude` dans les tests : `pam_check`,
  `spawn_bridge`, horloge et installeur injectés ; sockets dans `tempfile.mkdtemp()`.
- Jamais de mot de passe, secret TOTP, jeton, ticket ou cookie dans un journal, un message
  d'erreur, un test enregistré ou un commit. Les tests utilisent des valeurs fabriquées.
- Valeurs fixées par la conception : port `8420`, adresse `127.0.0.1` ; groupe Unix `ccs` ;
  `root` toujours refusé ; session : 12 h sans activité, 7 jours au plus ; appareil retenu
  30 jours (dispense du code, jamais du mot de passe) ; 5 échecs par utilisateur ou par IP
  en 15 min → refus 15 min ; pont arrêté après 12 h sans client et sans chat en cours ;
  service PAM `ccs` ; secrets TOTP dans `/var/lib/ccs/totp/<utilisateur>` (`0600 root`) ;
  sessions dans `/var/lib/ccs/sessions.json` (`0600 root`) ; sockets `/run/ccs/auth.sock`
  (`0660 root:ccs-web`) et `/run/ccs/bridge/<utilisateur>.sock`.
- Tous les chemins système passent par `ccs_app/server/paths.py` (surchargés par
  `CCS_SERVER_ROOT` dans les tests).
- Une ligne JSON fait au plus `MAX_LINE = 8 * 1024 * 1024` octets.

## Points de vigilance

1. **Mauvais mot de passe, utilisateur inconnu, hors du groupe `ccs` ou `root`** : même
   réponse (« Identifiant, mot de passe ou code incorrect »), aucun indice sur le motif.
   Test : tâche 5, `test_same_answer_for_every_refusal`.
2. **Le téléphone perd la connexion pendant un tour de Claude** : le chat continue dans le
   pont ; au retour, le client reçoit ce qu'il a manqué. Test : tâche 7,
   `test_reconnect_replays_missed_events`.
3. **Chemin hors du dossier de l'utilisateur** (`../../etc/shadow`, lien symbolique vers
   `/`) : refusé. Test : tâche 8, `test_paths_outside_home_refused`.
4. **Deux appareils sur le même chat** (téléphone et bureau) : mêmes événements ; une
   autorisation réglée sur l'un disparaît sur l'autre. Test : tâche 7,
   `test_two_clients_same_chat`.
5. **Trop gros** (ligne JSON de plus de 8 Mio, image énorme collée) : refus clair, la
   connexion et le pont tiennent. Tests : tâche 1, `test_line_too_long` ; tâche 11,
   `test_ws_oversized_message`.

### Task 5: service `ccs-auth`

**Fichiers :** créer `ccs_app/server/auth.py` ; modifier `ccs_app/cli.py` (commandes
cachées `ccs auth-serve`, et `ccs totp reinitialiser <utilisateur>` réservée à root) ; test
`tests/test_server_auth.py`.

**Interfaces :**
- Consomme : `rpc` (1), `totp`, `Limiter` (2), `TokenStore` (3), `pam_auth` (4).
- Produit : `class AuthService` : `__init__(tokens, pam_check=pam_auth.authenticate,
  allowed=pam_auth.allowed, spawn_bridge=start_bridge, clock=time.time, host="ccs.mawena.cloud")`
  et ces méthodes RPC (via `handlers()`), appelées par `ccs-web` seulement :
  - `login {user, password, code?, device?, ip}` → `{"status": "ok", "session", "ticket",
    "user", "device"?}` ou `{"status": "code"}` (code manquant) ou `{"status": "enroll",
    "pending", "qr_svg", "secret"}` (pas encore de secret : `pending` = jeton d'inscription,
    valable 10 min) ou `{"status": "refused", "message": "Identifiant, mot de passe ou code
    incorrect"}` ou `{"status": "blocked", "retry_after": s}`. `remember: true` →
    `device` (cookie 30 jours).
  - `enroll {pending, code, ip, remember?}` → comme `login` réussi (le secret n'est
    enregistré qu'ici).
  - `check {session}` → `{"user", "ticket"}` ou erreur `refuse`.
  - `logout {session}` ; `app_token {session, name}` → `{"token"}` ; `tokens {session}` ;
    `revoke {session, token_id}` ; `check_app {token}` → `{"user", "ticket"}`.
- Ticket : `hmac.new(bridge_key(user), session_hash, "sha256").hexdigest()` ;
  `bridge_key(user)` créée par `ccs-auth` (32 octets aléatoires, fichier `0600` appartenant à
  l'utilisateur) avant `spawn_bridge(user)`.
- `start_bridge(user)` : `systemctl start ccs-bridge@<user>.service` (`subprocess`,
  délai 20 s) ; attend le socket du pont.
- Délai constant : toute réponse `refused` part au plus tôt 1 s après la requête.
